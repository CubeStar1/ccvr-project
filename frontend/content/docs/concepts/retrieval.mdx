## What is searched

Every chunk contributes several pieces of text to the index: one description per picture
analyzer that ran on it, and its transcript. Each piece is stored with an embedding from
**OpenAI `text-embedding-3-small`** (1536 dimensions).

## How a search ranks chunks

A query is ranked two ways at once:

1. **Dense** — the query is embedded with the same model and compared against every piece by
   similarity of meaning.
2. **Lexical** — the query's words are matched against the same pieces as keywords.

The two rankings are fused with **reciprocal rank fusion**, then rolled up **per chunk**: a chunk's
score is `1/(k + best rank) + 0.5/(k + second-best rank)` with `k = 10`. A chunk whose
description *and* transcript both match ranks above one where only a single piece does.

So a quoted phrase finds the exact words, and a paraphrase still finds the right moment.

<Callout type="info">
  Scores are fused rank scores, not cosine similarities — they are small numbers (around 0.1 for
  a strong match) and only meaningful for ordering hits within one search. Don't threshold on
  them.
</Callout>

## Narrowing a search

| Parameter | Effect |
|---|---|
| `video_ids` | Only these videos. Omitted, every video in the backend is searched |
| `analyzer` | `default_video` (the default) searches everything. `ocr`, `people` or `object_detection` searches only that analyzer's descriptions |
| `limit` | How many chunks come back, 1–50 |

<Callout type="warn">
  The original core API also had `field`, `filters` and `score_threshold`. The backend accepts
  `field` and `score_threshold` but ignores them, and rejects a non-empty `filters` with a `400`.
  Narrow with `video_ids` and `analyzer`, and put everything else in the query text.
</Callout>

## Detail levels

The same result serves a browser and an agent, and they want opposite things. A page renders
every field cheaply; an agent pays for each one in context.

| Level | Contents |
|---|---|
| `minimal` | ids, timecodes, score, and a 240-character `snippet` |
| `standard` | plus `video_url`, `description`, `people`, `objects`, `actions`, `tags`, `speakers`, `turns`, `people_count` |
| `full` | plus the transcript `text`, `persons`, `detections` and on-screen `texts` |

The agent pattern is `detail=minimal` to decide, then
`GET /videos/{id}/chunks?chunk_ids=…` to read the few that matter.

## Search versus ask

### `POST /query` — find moments

Search, optionally with a written answer over the hits. Everything it knows comes from the
retrieved chunks.

Use it for "find the part where…", "when does…", "show me…".

### `POST /ask` — answer a question

Retrieves the moments most relevant to the question, **and** reads each video's `summary` and
`chapters` aggregates, then has the LLM answer from both. The overview is what lets it answer
whole-video questions that no single moment covers. `sources` reports which aggregates were read
for which video.

Use it for "what / why / how / summarise / explain" — anything where the answer is a conclusion
rather than a location.

## Citations

Both endpoints write answers from the evidence only, cite moments as `m:ss` timestamps, and say
plainly when the evidence doesn't answer the question. `/query`'s `answer` is `null` when nothing
matched or when `synthesize` is false.

Search hits are self-sufficient: everything needed to cite and play a moment — `video_id`,
`start`, `end`, `video_url` — is on the hit.
