## `video_id`

SHA-256 of the file's bytes, first 16 hex characters. **Content-derived, not the filename.**

Two different files both called `test.mp4` stay separate, and re-uploading the same file is
recognised as the same video rather than duplicated.

<Callout type="warn">
  Because it is a content hash, two callers who ingested the same bytes are referring to the
  *same* video. Whoever owns the application-side rows has to decide nothing else still points at
  it before deleting — the backend has no notion of who else is interested. The frontend's delete
  route counts references in `video_core` before telling the backend to remove anything.
</Callout>

The id does not exist until the bytes have been downloaded, which is why ingest returns a job id
rather than a video id, and why the row in `video_core` is created with `core_video_id` null.

## `chunk_id`

Position within one video's chunk list. **Not globally unique** — every video has a chunk 0, so
always pair it with a `video_id`. It is also not stable across re-chunkings: chunk 12 of one run
is a different moment than chunk 12 of another.

## `chunk_config`

Which chunking policy produced the chunks: `scene`, `vad`, `speaker` or `uniform`. See
[Chunking](/docs/concepts/chunking).

## `analyzer`

One per-chunk pass. The picture analyzers map onto VIDRA samplers (`default_video` → `uniform`,
`ocr` → `text`, `people` → `yolo`, `object_detection` → `objects`); `transcript` and
`diarization` process the soundtrack. See [Analyzers](/docs/concepts/analyzers).

## `sampler`

VIDRA's word for a picture analyzer: the rule that decides which frames of a chunk are worth
sending to the vision model.

## `aggregate`

One video-level result, computed from stored chunk output. See
[Aggregators](/docs/concepts/aggregators). Some have different names in VIDRA's files than in the
API: `speakers` → `speaker_stats`, `entities:people` → `entities`, `entities:objects` →
`object_entities`, `entities:text` → `text_entities`.

## `tier`

What an aggregate costs: `free` (counting), `local` (a small model on your machine) or `llm` (an
API call). `VIDRA_TIER` caps which tiers run at ingest.

## `job_id`

A 12-character hex id for a background job. Ingest and aggregate re-runs both return one.

<Callout type="info">
  Jobs are saved to `data/jobs/` as they change, so they survive a restart. A job that was still
  running when the backend stopped is reported as `failed` with "the server restarted while this
  job ran" — re-index to try again.
</Callout>

## Video folder

`data/out/<video_id>/`: everything VIDRA produced for one video — media info, timeline,
transcript, descriptions, embeddings and aggregates. It is also that video's search index.
`GET /videos/{id}/chunks` and `GET /videos/{id}/aggregates` read straight from it, so they cost
nothing.

## `detail`

How much of a search hit comes back: `minimal`, `standard` or `full`. See
[Retrieval](/docs/concepts/retrieval).

## Application-side terms

These exist in the frontend only; the backend has never heard of them.

| Term | Meaning |
|---|---|
| **Project** | A workspace owning videos and conversations. Row in `projects`, scoped by RLS |
| **Conversation** | One chat thread inside a project. Rows in `conversations` / `messages` |
| **Video row** | A row in `video_core` — the application's view of a backend video, plus ownership and ingest state |
| **Clip** | A `(video_id, url, start, end)` tuple. Not a stream of its own: the panel loads the mp4 once and seeks |
| **Artifact panel** | The right-hand surface that renders clip reels and long documents |
