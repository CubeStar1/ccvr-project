Ingestion is one background job that runs VIDRA's `workflow()` over the video. Each stage
reports itself on the job, so a client polling `GET /jobs/{job_id}` can show where a video is.

```
fetching ─▶ transcribing ─▶ chunking ─▶ sampling ─▶ analyzing ─▶ indexing ─▶ aggregating ─▶ publishing ─▶ complete
```

## 1. Fetching

The backend takes the uploaded file, or downloads the source URL, into `data/sources/`, hashing
the bytes.
The first 16 hex characters of the **SHA-256** become the **video id** — so the same file is
always the same video, and two different files that share a name stay separate.

PyAV then probes the file for its duration, frame rate and streams (`media.json`).

## 2. Transcribing

Only when `transcript` or `diarization` was selected.

| Step | Model | Runs on |
|---|---|---|
| Speech to text | **faster-whisper `small`**, int8, with voice-activity filtering | Your machine |
| Who is speaking | **pyannote `speaker-diarization-3.1`** — `diarization` only | Your machine |

Speech is transcribed once for the whole track (`transcript.raw.json`), before chunking, because
two of the chunking policies cut on speech.

## 3. Chunking

The video is cut into chunks — the unit everything below is attached to, and what a search hit
points at. Cuts follow scene changes, speech pauses or speaker turns depending on the upload's
chunking choice, and every chunk ends up between 5 and 20 seconds.

See [Chunking](/docs/concepts/chunking).

## 4. Sampling

Sending every frame to a vision model would be slow and expensive, so each picture analyzer
picks a handful of frames per chunk with its own local detector, and near-duplicates are
dropped. See [Analyzers](/docs/concepts/analyzers).

The transcript is also cut onto the chunks here, so each chunk carries the words spoken inside it.

## 5. Analyzing

For each chunk and each picture analyzer, the chosen frames are sent to the vision model —
**OpenAI `gpt-6-luna`** — with a fixed JSON schema. It returns a prose description plus
structured fields: setting, people, objects, actions, changes, tags and visible text
(`descriptions.json`).

This is usually the longest stage, and the one that costs money.

## 6. Indexing

Each chunk's descriptions and transcript are embedded with **OpenAI `text-embedding-3-small`**
(1536 dimensions) and written to the video's folder, which doubles as the search index. See
[Retrieval](/docs/concepts/retrieval).

## 7. Aggregating

Video-level passes run over what was just written — not over the video. That is what makes
re-summarising cheap: nothing has to be re-analysed. Which ones run depends on `VIDRA_TIER` and
on which analyzers ran. See [Aggregators](/docs/concepts/aggregators).

A poster frame (one second in) is saved last, for the video card.

## 8. Publishing

With blob storage configured, the finished video — file, folder, poster and metadata — is copied
to Azure Blob Storage, and the local copy of the video file is dropped. Without it, this stage
does nothing.

## What gets written

Everything lands under `backend/data/`:

| Where | What |
|---|---|
| `out/<id>/media.json` | Duration, frame rate, streams |
| `out/<id>/transcript.raw.json`, `transcript.json` | Whisper output for the whole track, then cut per chunk |
| `out/<id>/timeline.json` | The chunk spans, and which policy produced them |
| `out/<id>/descriptions.json` | The vision model's answer per chunk per analyzer |
| `out/<id>/embedded.json`, `store/` | The embeddings and the search index |
| `out/<id>/aggregates/*.json` | One file per video-level result |
| `out/<id>/manifest.json` | What ran, with which models and settings |
| `sources/`, `posters/`, `videos/`, `jobs/` | The video file, its poster, the ingest request, job state |
| `uploads/` | Browser uploads waiting to be ingested, and a record per upload |

In production all of it is mirrored to Azure Blob Storage — see
[Deployment](/docs/getting-started/deployment).

## Re-running

Re-indexing from the app hands the backend the same source URL again. The bytes hash to the same
video id, so the pipeline runs again into the same folder — with the analyzers and chunking now
asked for.

<Callout type="info">
  Aggregates can be re-run on their own with `POST /videos/{video_id}/aggregates`. Since they
  read stored output rather than the video, that costs no re-analysis — only the LLM calls for
  the aggregates that make them.
</Callout>

## Timing

Ingestion takes minutes, which is why the ingest route returns `202` and a job id rather than
holding the connection open. As a reference point: a 5-minute screen-recorded tutorial with
`default_video`, `diarization` and `ocr` came out as 24 chunks and 312 kept frames, and took
about 5½ minutes on an Apple Silicon laptop. Frame sampling alone took 35 seconds.

The backend processes **one video at a time**; a second upload waits in `queued` until the first
finishes.
