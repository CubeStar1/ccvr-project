## Requirements

**backend** needs [uv](https://docs.astral.sh/uv/), ffmpeg, an OpenAI API key and a Hugging Face
token. uv installs Python itself — the backend pins 3.12 and accepts 3.11–3.13. PyTorch picks the
best device available: `mps` on Apple Silicon, CUDA on an NVIDIA GPU, otherwise CPU.

**frontend** needs Node 20+ and a Supabase project.

- `vidra/` is the engine, a Python library. The backend installs it as an editable dependency,
  so a change there takes effect on the next server start.
- `backend/app.py` is the HTTP layer; `backend/engine.py` holds the logic: jobs, ingest, and
  reading VIDRA's output back in the shapes the frontend expects.
- `backend/data/` holds every piece of runtime state. Deleting it is a full reset.

## 1. Backend

### Install

```bash
cd backend
uv sync
```

This creates `backend/.venv` with VIDRA and all its models' libraries (faster-whisper, pyannote,
ultralytics, transformers, GLiNER, OpenCV).

### Environment

```bash title="backend/.env"
OPENAI_API_KEY=sk-...
HF_TOKEN=hf_...
```

`HF_TOKEN` is used for speaker diarization. Its models are gated: sign in to Hugging Face and
accept the terms on
[pyannote/speaker-diarization-3.1](https://huggingface.co/pyannote/speaker-diarization-3.1) and
[pyannote/segmentation-3.0](https://huggingface.co/pyannote/segmentation-3.0) first, or
diarization fails when it loads.

The optional variables are in [Configuration](/docs/getting-started/configuration).

### Run

```bash
uv run uvicorn app:app --port 8077
uv run uvicorn app:app --port 8077 --reload        # restart on code changes
uv run uvicorn app:app --host 0.0.0.0 --port 8077  # reachable from the LAN — set CORE_API_TOKEN
```

`/` redirects to the Swagger docs at `/docs`. There is no built-in UI; the frontend is the UI.

<Callout type="info">
  Model weights download on first use and are cached by Hugging Face and Ultralytics, so the
  first ingest is noticeably slower than the rest. `*.pt` files that land in `backend/` are
  git-ignored.
</Callout>

## 2. Database

Run `frontend/lib/supabase/migrations/schema.sql` in the Supabase SQL editor. It creates
`projects`, `conversations`, `messages`, `video_core`, the `project-assets` bucket,
`update_updated_at()`, and the RLS policies.

### The `video_core` table

This is the join between the application's world and the backend's.

| Column | Purpose |
|---|---|
| `project_id`, `user_id` | Ownership. RLS restricts every row to `auth.uid() = user_id` |
| `title`, `source_type`, `source_url` | Where the video came from: a URL, or `upload:<id>` for a file uploaded to the backend |
| `storage_path` | Only set on rows from before uploads went to the backend: the file's path in `project-assets` |
| `core_video_id` | The backend's identity — `sha256(bytes)[:16]`. Null until the backend has downloaded the file |
| `playback_url`, `poster_url`, `duration`, `size_bytes` | Written back from the ingest job result |
| `status`, `job_id`, `stage`, `progress`, `error` | Ingest lifecycle, reconciled on every poll |
| `ingest_config` | What the pipeline was asked for, replayed verbatim on re-index |
| `analyzers`, `aggregates`, `chunk_config`, `chunk_count` | What it actually produced |

<Callout type="warn">
  `core_video_id` is unique **per project**, never globally: the same file uploaded to two
  projects is one video in the backend. Deleting one project's row must not delete the backend's
  video while another row still points at it — the delete route counts references first.
</Callout>

### Email confirmation codes

Sign-up sends a one-time code by email. The sign-up form expects **8 digits**, which is
Supabase's current default. If your project sends a different length (Authentication → Email →
"Email OTP Length"), change `OTP_LENGTH` in `frontend/components/supaauth/signup.tsx` to match.

## 3. Frontend

```bash
cd frontend
npm install
cp env.example .env.local
npm run dev
```

The full variable list is in [Configuration](/docs/getting-started/configuration). At minimum
you need the three Supabase values, one model provider key, and `CORE_API_URL`.

## Verifying the install

```bash
curl http://127.0.0.1:8077/health
```

```json
{
  "status": "ok",
  "engine": "vidra 3.0.0",
  "tier": "llm",
  "data": "/path/to/backend/data",
  "videos": 0,
  "analyzers": ["default_video", "transcript", "diarization", "ocr", "people", "object_detection"],
  "aggregators": ["chapters", "coverage", "entities", "events", "ner", "object_entities",
                  "sentiment", "speaker_stats", "stats", "summary", "text_entities"],
  "ffmpeg": "/opt/homebrew/bin/ffmpeg"
}
```

Then, from the frontend, sign in and open `/projects`. If the upload dialog's analyzer list
populates, the frontend can reach the backend — that list is built from
`GET /api/core/capabilities`, which proxies the backend's `/analyzers` and `/schema`.

## Resetting

Everything the backend writes lives under `backend/data/` (or `BACKEND_DATA`):

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
rm -rf backend/data
```

</Tab>
<Tab value="PowerShell">

```powershell
Remove-Item -Recurse -Force backend/data
```

</Tab>
</Tabs>

Application rows survive in Postgres, so after a reset those videos have nothing behind them —
not even the video file, which the backend stores. Delete those rows and upload again. Videos
added by URL can be re-indexed, as long as the URL still works.
