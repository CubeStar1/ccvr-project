## The shape

```
browser
  │
  ▼
Next.js app ──► Supabase  (auth · Postgres)
  │
  │  HTTP, server-side only  (lib/core/client.ts, X-Core-Token)
  ▼
backend/app.py ──► backend/engine.py ──► vidra (library) ──► backend/data/ ◄──► Azure Blob Storage
  (FastAPI)          (jobs, shapes)         │                   (cache)          (when configured)
                                            ├─ local: Whisper, pyannote, OpenCV, YOLO, CLIP, GLiNER, DistilBERT
                                            └─ OpenAI: vision model, embeddings, LLM
```

| Component | Owns |
|---|---|
| **Next.js app** | Auth, projects, ownership, conversations, the agent loop, all UI |
| **Supabase** | Users, and the `projects` / `conversations` / `messages` / `video_core` tables with RLS |
| **backend** | The HTTP API, uploads, playback, background jobs, and translating VIDRA's output into the API's response shapes |
| **vidra** | Everything about understanding a video: transcription, chunking, frame sampling, description, embedding, search, aggregates |
| **backend/data** | Every video file, and its folder of analysis, which is also its search index. No database server. In production, mirrored to Azure Blob Storage and only a cache on the container's disk |

<Callout type="info">
  The backend kept the routes and response shapes of the original `core/` service, so the
  frontend's client, tools and pages work unchanged. `engine.py` is where VIDRA's vocabulary —
  samplers, policies, aggregate ids — is mapped onto the old one.
</Callout>

## Ingesting a video

```
browser ──POST /api/uploads──► backend: POST /uploads ──► one-time signed URL
   │
   ├──PUT file──► Azure Blob Storage  uploads/<upload_id>/…   (the backend itself, in development)
   │
   └──POST /api/videos  { sourceUrl: "upload:<upload_id>" }   (or a pasted http(s) URL)
              │
              ├─► insert video_core row (status: pending)
              └─► POST /videos/url ──► backend: 202 + job_id
                                        │
                                        └─► worker thread (one video at a time):
                                            take the upload, or download the URL
                                            → vidra.workflow() → poster → publish to blob
                                                │
                                                ├─► sources/<id>   the video, stored once
                                                ├─► out/<id>/      transcript, chunks, descriptions,
                                                │                  embeddings, aggregates
                                                └─► jobs/          job state, every stage

browser ──poll /api/videos──► reconcile row against GET /jobs/{id} ──► status: ready
browser ──<video src=/media/<id>>──► backend ──307──► signed blob URL
```

The row exists before the backend has seen a byte, because the video's id is the hash of its
contents. Everything identifying arrives later, through the job. Video bytes never pass through
Vercel or Supabase.

## Answering a question

```
user message
   │
   ▼
POST /api/agent
   ├─ load the project's video_core rows  (RLS)
   ├─ build a system prompt carrying each video's analyzers and aggregates
   └─ streamText with the video tools, up to 15 steps
        │
        ├─ tool call ──► resolveScope()  ──► allowed core_video_ids
        │                                     │
        │                                     ▼
        │                       backend: POST /query | /ask | GET /chunks | /aggregates | /entities
        │                                     │
        │                                     └─► vidra search over data/out, or a file read
        │
        ├─ show_clips ──► (no backend call) ──► artifact panel renders the reel
        │
        └─ stream text + tool parts ──► client
                                          │
                                          └─► persist messages to Postgres
```

The agent never receives a raw backend response. Every tool reshapes it: timestamps into `m:ss`,
`video_id` into the row's `playback_url` and title, and the backend's error messages passed through
as written, because they are meant to be the correction the model needs.

Two different models are involved in a chat. The **chat model** — whichever one is picked in the
model selector — runs the agent loop and writes the reply. The **backend's models** (OpenAI by
default) understood the video at ingest, and write the answers `/query` and `/ask` return.

## Inside the backend

```
backend/
  app.py       FastAPI routes; validation and error translation only
  engine.py    jobs, download, ingest, and every read in the API's shapes
vidra/vidra/
  workflow.py  the whole ingest, start to finish
  video_rag/   media probe, audio, boundaries, samplers, describe, embed, search
  aggregates/  the eleven video-level passes, by tier
  shared/      model roles, storage backends, contracts
```

`app.py` is deliberately thin. All logic lives in `engine.py`, which is importable — a script, a
CLI or an MCP server is a new caller, not a new implementation.

## Decisions worth knowing

**The video is downloaded, not streamed.** Every stage re-opens the file and seeks per chunk —
an access pattern priced for a local disk. The backend brings the source to `data/sources/` once
and every stage reads that copy.

**Files, not a database server.** VIDRA's `Folder` store keeps each video's index in its own
folder. Nothing to run or migrate, and deleting a video is deleting a folder.

**Blob storage as the system of record, local disk as a cache.** In production `blobs.py`
mirrors the data folder to Azure Blob Storage, and a video's files are pulled back the first time
it is read. The container can be restarted or replaced without losing anything.

**Browsers talk to storage only through signed URLs.** An upload gets a write URL for one blob,
valid 30 minutes; playback gets a read URL, valid 3 hours, behind a `307` from `/media/<id>`. The
container stays private, and video bytes skip both Vercel and the backend's CPU.

**One ingest at a time.** Every ingest loads Whisper, pyannote and the detectors onto the same
GPU. A single worker keeps memory predictable; extra uploads wait in `queued`.

**A clip is a range, not a stream.** There is no per-clip URL anywhere. The panel loads the mp4
once and seeks, so several clips from one video cost one load between them.

## Deployment shape

| Piece | Where |
|---|---|
| Next.js app | Vercel |
| backend | Azure Container Apps, CPU, one replica — built by `.github/workflows/deploy-backend.yml` |
| Video files and analysis | Azure Blob Storage |
| Postgres + Auth | Supabase Cloud |

Step by step in [Deployment](/docs/getting-started/deployment).

<Callout type="warn">
  The backend's port must not be publicly routable. It has no users and no row-level security —
  `CORE_API_TOKEN` is a boundary, not an authorisation model. See
  [Authentication](/docs/api/authentication).
</Callout>

## Known limitations

- **Chunk length is fixed** at 5–20 s, and fixed intervals at 20 s. VIDRA's `workflow()` doesn't
  take the upload dialog's bounds yet.
- **No structured search filters.** `/query` rejects `filters`; `field` and `score_threshold`
  are ignored.
- **Direct video URLs only.** YouTube and other page links aren't downloaded, even though the
  agent's `add_video` tool describes YouTube support.
- **One ingest at a time.**
- **Entity linking is within one video.** The same person in two videos is two entities.
