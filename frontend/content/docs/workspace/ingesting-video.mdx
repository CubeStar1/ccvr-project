## The upload dialog

**Upload** in the project workspace opens a dialog with two halves: where the video comes from,
and how it should be analysed.

### Sources

- **Files** — dropped or picked, accepting `video/*`. Each file is uploaded to the project's
  Supabase Storage bucket (`project-assets`) first; the resulting public URL is what the backend
  is handed.
- **URLs** — any direct `http(s)` link to a video file. Nothing is copied to Storage on this path;
  the backend downloads it itself. Links to pages, such as YouTube, are not supported.

Several of each can be queued at once. Each source becomes its own job with its own progress row
in the dialog.

<Callout type="warn">
  Supabase caps uploads at 50 MB by default. Raise the bucket limit, or add large videos by URL
  instead — that path never pushes the bytes through the browser.
</Callout>

### Analyzers

The list is built at runtime from `GET /api/core/capabilities`, which proxies the backend's
`/analyzers` and `/schema`. It is not a hardcoded constant, so an analyzer added to the backend
appears here without a frontend change.

Each option shows what it produces and whether it bills per chunk. `transcript` and `diarization`
are mutually exclusive, and the dialog greys the second one out rather than letting the submit
fail with a `400`.

Default selection: `default_video` + `diarization`. Add `ocr` for slides and screen recordings.
See [Analyzers](/docs/concepts/analyzers).

### Chunking

Three modes:

| Mode | Control | Becomes |
|---|---|---|
| **Preset** | `Audio + video`, `Audio-led` or `Video-led` | Scene cuts, or speech pauses for `Audio-led` |
| **Custom weights** | Sliders for `speaker`, `silence`, `cut`, `semantic` | The policy for the heaviest-weighted signal |
| **Fixed interval** | Seconds per chunk | Fixed 20-second chunks |

<Callout type="warn">
  Chunks are always kept between 5 and 20 seconds, and fixed intervals are always 20 seconds. The
  *shortest*, *longest* and *seconds per chunk* fields are saved but have no effect yet. See
  [Chunking](/docs/concepts/chunking).
</Callout>

The chosen config is stored on the row as `ingest_config` and replayed verbatim on re-index.

## What happens on submit

<Steps>

<Step>
### The row is created first

Before the backend has seen a byte. The video's id is the hash of its contents, so it does not
exist until the download finishes — everything identifying arrives later, through the job.
</Step>

<Step>
### The backend is handed the URL

`POST /videos/url` returns `202` and a job id, which is written to the row along with
`status: 'queued'`.

If the backend is unreachable, the row is marked `failed` with the reason, and the API responds
`502`. The video is still in the list, and **Re-index** is the way out.
</Step>

<Step>
### Progress is reconciled on poll

Each poll of `GET /api/videos?projectId=…` brings any in-flight row up to date with the job it is
waiting on, and persists what changed. The row's status follows the job's status, and the job's
`stage` is copied alongside it:

| Job status | Row status | `stage` while there |
|---|---|---|
| `queued` | `queued` | `queued` |
| `running` | `analyzing` | `fetching`, `transcribing`, `chunking`, `sampling`, `analyzing`, `indexing`, `aggregating` |
| `done` | `ready` | `complete` |
| `failed` | `failed` | wherever it stopped |
</Step>

<Step>
### The result is written back

When the job finishes, the row gains `core_video_id`, `playback_url`, `poster_url`, `duration`,
`size_bytes`, `chunk_config`, `chunk_count`, `analyzers` and `aggregates`. Only then is the video
`ready` and searchable.
</Step>

</Steps>

## Statuses

| Status | Meaning |
|---|---|
| `pending` | Row created, backend not yet called |
| `uploading` | The browser is still pushing bytes to Storage |
| `queued` | The backend accepted the job; it may be waiting behind another video |
| `analyzing` | The backend is working — `stage` says which part |
| `ready` | Searchable |
| `failed` | `error` says why. Re-index to retry |

## Re-indexing

Available from the card menu. There is no separate re-index call in the backend: the same source
URL hashes to the same video id, so handing it over again re-runs the pipeline into the same
video, with whatever analyzers and chunking are now asked for.

## Deleting

Deleting a video removes its row. The backend is only told to delete its copy once **nothing
else references it**: the same file uploaded to two projects is one video in the backend, and
destroying it because this row went away would destroy the other project's analysis.

When the backend does delete, it removes the video's folder (and with it the search index), the
downloaded file, the poster and the ingest record in one call.
