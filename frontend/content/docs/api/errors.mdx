## Shape

Errors are FastAPI's standard envelope:

```json
{ "detail": "Unknown or missing analyzers ['peple']; have ['default_video', 'transcript', 'diarization', 'ocr', 'people', 'object_detection']" }
```

Messages are written to be actionable. Asking for an aggregate a video doesn't have returns the
list of what it *does* have; an unknown analyzer returns the valid ones.

## Status codes

| Code | Meaning | Typical cause |
|---|---|---|
| `200` | Success | – |
| `202` | Accepted, work started in the background | Ingest, and the aggregate re-run |
| `307` | Redirect | `/` → `/docs` |
| `400` | Bad request | Unknown analyzer, chunking mode, detail level or aggregate; mutually exclusive analyzers; a non-`http(s)` URL; a non-empty `filters`; malformed `chunk_ids` |
| `401` | Unauthorised | Missing or wrong `X-Core-Token` |
| `404` | Not found | Unknown `video_id`, `chunk_id` or `job_id`; a missing poster |
| `422` | Unprocessable | FastAPI validation — a wrong type, or a value outside a declared range |
| `500` | Server error | An unhandled failure. The traceback is in the server's output |

## Request-time versus job-time failures

<Callout type="warn">
  Anything that can be checked while the caller is still there **is** checked before the `202`.
  Everything after that fails the **job**, not the request.
</Callout>

Validated up front, returning `400`:

- Unknown or missing analyzer ids, and the mutually exclusive pair (`transcript` + `diarization`).
- An unknown chunking `mode`.
- A URL whose scheme is not `http` or `https`.

Discovered later, failing the job:

- A URL that 404s or can't be reached.
- A file that can't be decoded.
- A model provider error — a bad OpenAI key, a rate limit, an outage.
- A gated Hugging Face model that the token can't access.

```json
{
  "job_id": "d9b16a609ab1",
  "status": "failed",
  "stage": "fetching",
  "error": "HTTPStatusError: Client error '404 Not Found' for url 'https://example.com/missing.mp4'",
  "result": null
}
```

## Partial failure

Some operations deliberately degrade rather than fail:

| Situation | Behaviour |
|---|---|
| An aggregate fails during ingest | The ingest still succeeds and the video is searchable; `aggregated.error` says what went wrong |
| An aggregate's analyzer never ran | Listed in `skipped` with the reason, not treated as a failure |
| Poster extraction fails | `poster_url` is null; the ingest still succeeds |
| An audio-based chunking policy on a file with no soundtrack | Falls back to fixed 20-second chunks |
| An analyzer produces nothing for a chunk | That chunk has no output for it; `indexed` counts drop accordingly |

<Callout type="info">
  A zero in `indexed` is normal, not an error — a silent video produces no transcript text.
</Callout>

## Failure modes worth designing for

**A restart mid-ingest.** Jobs are saved to disk. A job that was `queued` or `running` when the
backend stopped comes back as `failed` with `"the server restarted while this job ran"`. Re-ingest
to recover.

**Backend unreachable.** A client should distinguish "the backend said no" from "the backend did
not answer" — the reference client wraps connection failures as a `503` with the URL it tried,
because those two cases need very different messages in a UI.
