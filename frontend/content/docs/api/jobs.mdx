Ingestion and aggregate re-runs both execute on a worker thread and report progress on a job.
Poll until `status` is `done` or `failed`.

---

## `GET /jobs/{job_id}`

```json
{
  "job_id": "d9b16a609ab1",
  "status": "running",
  "stage": "analyzing",
  "detail": { "source": "https://example.com/clip.mp4", "analyzers": ["default_video", "diarization"] },
  "result": null,
  "error": null,
  "created_at": "2026-10-28T09:12:03.512409+00:00",
  "updated_at": "2026-10-28T09:14:41.077215+00:00"
}
```

| Field | Meaning |
|---|---|
| `status` | `queued` → `running` → `done` \| `failed` |
| `stage` | Where in the pipeline it is |
| `detail` | What the job was asked to do |
| `result` | The result object once `done`; `null` before that |
| `error` | `"TypeName: message"` when `failed`, else `null` |
| `created_at`, `updated_at` | ISO 8601, UTC |

### Stages

| Stage | What is happening |
|---|---|
| `queued` | Waiting for the worker — one job runs at a time |
| `fetching` | Taking the upload or downloading the URL, hashing it, probing the file |
| `transcribing` | Whisper (and pyannote for `diarization`), then cutting the transcript onto chunks |
| `chunking` | Finding scene or speech boundaries |
| `sampling` | Choosing frames per chunk for each picture analyzer |
| `analyzing` | The vision model describing each chunk |
| `indexing` | Embedding descriptions and transcript |
| `aggregating` | Video-level passes |
| `publishing` | Copying the finished video to blob storage (a no-op without it) |
| `complete` | Done |

### Ingest result

```json
{
  "video_id": "dbf7af7300ab2484",
  "video_url": "http://127.0.0.1:8077/media/dbf7af7300ab2484",
  "poster_url": "http://127.0.0.1:8077/media/dbf7af7300ab2484/poster.jpg",
  "storage_path": "sources/dbf7af7300ab2484.mp4",
  "filename": "clip.mp4",
  "duration": 311.433,
  "size_bytes": 16135088,
  "chunk_config": "scene",
  "chunks": 24,
  "analyzers": ["default_video", "diarization", "ocr"],
  "indexed": { "default_video": 24, "diarization": 23, "ocr": 24 },
  "aggregated": {
    "ran": ["chapters", "coverage", "events", "ner", "sentiment", "speaker_stats",
            "stats", "summary", "text_entities"],
    "aggregates": ["chapters", "coverage", "events", "ner", "sentiment", "speaker_stats",
                   "stats", "summary", "text_entities"]
  }
}
```

`video_url` is where the video plays from — this server's `GET /media/{video_id}`.

<Callout type="info">
  `indexed` counts chunks with output per analyzer. A zero is normal, not an error — a silent
  video produces no transcript text.
</Callout>

If an aggregate failed, `aggregated` also carries `error`; the ingest itself still succeeded and
the video is searchable.

### Aggregate re-run result

A job started by `POST /videos/{video_id}/aggregates` resolves to
`{ video_id, ran, aggregates, skipped }` — see [Aggregates](/docs/api/aggregates). The two kinds are distinguishable by the presence of
`video_url`, which only an ingest result has.

## Polling strategy

Ingestion takes minutes — a five-minute video takes around five. A poll every few seconds is
plenty.

<Callout type="info">
  Jobs are written to `data/jobs/` (and blob storage, when configured) on every change, so a
  restart doesn't lose them. A job that was still `queued` or `running` when the backend stopped
  is reported as `failed` with
  `"the server restarted while this job ran"`. Re-ingest to recover.
</Callout>

**404** for an unknown job id.
