## `POST /videos/url`

`application/json`. Download a video from a URL and analyse it. Returns **`202`** immediately,
because ingestion takes minutes.

### Body

| Field | Type | Default | Notes |
|---|---|---|---|
| `url` | string | *required* | A direct `http(s)` link to a video file |
| `analyzers` | string | `default_video` | Comma-separated ids. See [Analyzers](/docs/concepts/analyzers) |
| `mode` | string | `preset` | `preset` \| `weights` \| `interval` |
| `preset` | string | `audio_video` | `mode=preset` only: `audio` \| `video` \| `audio_video` |
| `speaker`, `silence`, `cut`, `semantic` | float \| null | `null` | `mode=weights` only; the heaviest one picks the policy |
| `interval` | float \| null | `null` | Accepted; chunks are always 20 s in `interval` mode |
| `min_duration`, `max_duration` | float | `5`, `20` | Accepted; the bounds are always 5–20 s |

### Example

```bash
curl -X POST http://127.0.0.1:8077/videos/url \
  -H "X-Core-Token: $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
    "url": "https://example.com/clip.mp4",
    "analyzers": "default_video,diarization,ocr",
    "mode": "preset",
    "preset": "audio_video"
  }'
```

```json
{ "job_id": "d9b16a609ab1", "status": "queued", "source": "https://example.com/clip.mp4" }
```

<Callout type="info">
  `video_id` is the hash of the bytes, so it does not exist until the download finishes. It
  arrives in the job result along with `video_url`. Design your rows for that: create them before
  the id exists, and fill it in from the job.
</Callout>

<Callout type="warn">
  The URL must serve the video file itself. A page that embeds a video — YouTube, Vimeo, a share
  page — downloads as HTML and the job fails. Uploading a file means putting it in storage first
  (the frontend uses Supabase Storage) and passing that URL.
</Callout>

## Chunking modes

Each mode is mapped onto one of VIDRA's chunking policies:

| Body | Policy |
|---|---|
| `mode=preset`, `preset=audio_video` or `video` | `scene` |
| `mode=preset`, `preset=audio` | `vad` |
| `mode=weights` | The heaviest signal: `speaker` → `speaker`, `silence` → `vad`, `cut` / `semantic` → `scene` |
| `mode=interval` | `uniform` (20 s) |

If the policy needs a signal the analyzers don't provide, the backend falls back — `vad` without
a speech analyzer becomes `scene`, and so on — and a file with no soundtrack falls back to
`uniform`. The policy actually used comes back as `chunk_config`. See
[Chunking](/docs/concepts/chunking).

## Re-ingesting

There is no separate re-index endpoint. The same bytes hash to the same `video_id`, so posting
the same URL again re-runs the pipeline into that video's folder, with the analyzers and chunking
now asked for.

Jobs run **one at a time**. A second request is accepted straight away and its job stays `queued`
until the first finishes.

## Errors

| Code | Cause |
|---|---|
| `400` | Unknown or missing analyzers; `transcript` + `diarization` together; unknown `mode`; a non-`http(s)` URL |
| `401` | Missing or wrong token |

A URL that 404s or isn't a decodable video fails the **job**, not the request — the download
starts after the `202`. See [Errors](/docs/api/errors).
